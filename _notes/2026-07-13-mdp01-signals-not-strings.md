# Signals, Not Strings

The CBR routing strategy had a design problem hiding in plain sight. `CbrAgentRoutingStrategy` hardcoded its outcome weights as a `Map<String, Double>` — SUCCESS at 1.0, GATE_EXPIRED at 0.5, and so on. Every domain got the same weights whether they were routing AML investigators or clinical specialists. The fix was straightforward: extract into an injectable `CbrOutcomeWeights` SPI with a `@DefaultBean` providing the current values. Domain repos override with `@ApplicationScoped`.

But the interesting discovery came when we traced what happened to `RoutingFeatureExtractor`. The SPI was designed, implemented, deployed to domain repos (AML and clinical both had custom implementations) — and then quietly deleted when `CbrAgentRoutingStrategy` switched to reading pre-retrieved experiences from `context.experiences()`. The engine's `CbrRetrievalService` now owns feature extraction via `CbrConfig` — JQ expressions or lambdas configured at the case definition level. The domain implementations are orphaned code implementing a deleted interface.

What I hadn't noticed until this session: the strategy was also ignoring `RetrievedExperience.similarityScore()`. Every experience contributed equally to worker scoring regardless of how well it matched the current case. A 0.95-similarity past case counted the same as a 0.3. The fix weights each experience's contribution by its similarity, with negative scores clamped to zero — anti-similar cases shouldn't invert the scoring.

The bigger piece was `RoutingSignalProvider` — a structured enrichment SPI parallel to `RoutingPromptSection`. The prompt section pipeline works well for LLM strategies: each section renders text, the assembler concatenates, the LLM reasons over it. But `CbrAgentRoutingStrategy` is algorithmic — it needs structured per-candidate scores, not prompt text. `RoutingSignalProvider` returns `RoutingSignal` with per-candidate scores in [0.0, 1.0], assembled by `RoutingSignalAssembler` with the same priority ordering and exception resilience as the prompt assembler.

The first implementation of this SPI is `PlanCompositionAnalyser` — it scores candidates based on case-level outcomes in multi-step plans. A worker that appeared in COMPLETED multi-step cases scores higher than one that appeared in FAULTED cases, even if the individual step outcomes were identical. The plan structure context is orthogonal to single-step analysis.

The design review caught real issues. Negative similarity scores could invert the arithmetic. The tie-breaker cast evidence mass to int, losing precision. Step-level outcomes (`RoutingOutcome` enum) and case-level outcomes (domain-dependent strings like COMPLETED, FAULTED) were being conflated in a single weight map. Signal scores needed normalisation to [0.0, 1.0] to prevent dimensional inconsistency when combining with experience scores. Each of these was a genuine bug that tests alone wouldn't have surfaced — the review paid for itself.
